## 0. Контекст и правила игры

**Что строим (фаза 1):** ManiSkill-среду с двумя руками SO-100, которые учатся поворачивать грань «поворотного» кубика; децентрализованный MARL-бейзлайн (IPPO/MAPPO); затем модуль Bi-JEPA (предсказание партнёра) в пространстве состояний.

**Железо/окружение (важно!):**
- Разработка – на macOS; **симуляция ManiSkill на маке НЕ запускается** (нужен Linux + NVIDIA/CUDA). Значит:
  - код должен **импортироваться и проходить линт на маке**;
  - всё, что трогает симуляцию, **запускается только на сервере** (`bash scripts/setup_server.sh`, затем `uv run ...`);
  - модули на чистом PyTorch (энкодеры/предсказатель Bi-JEPA, парсинг конфигов) – **тестируются на маке** через `pytest`.
- Python 3.12, менеджер `uv`. Установка dev-окружения: `make dev`. Полное (сервер): `bash scripts/setup_server.sh`.

**Правила для кодера (обязательно):**
1. **Не выдумывай API.** Перед каждым шагом читай файлы-референсы ManiSkill (список ниже) и копируй реальные сигнатуры.
   - ⚠️ **Локально (macOS) ManiSkill НЕ установлен** — в `pyproject.toml` он помечен `sys_platform == 'linux'`. В `.venv` его нет, читать оттуда нечего.
   - Читай **с GitHub на теге, совпадающем с локом**: у нас `mani-skill == 3.0.1` → тег **`v3.0.1`** (не `main`, он уже разошёлся).
   - Быстрый способ (gh авторизован):
     `gh api "repos/haosulab/ManiSkill/contents/<путь>?ref=v3.0.1" --jq .content | base64 -d`
     или в браузере: `https://github.com/haosulab/ManiSkill/blob/v3.0.1/<путь>`
   - Если понадобится API, которого на `v3.0.1` нет — **не бери его с `main`**, сообщи в отчёте.
2. **Маленькие шаги.** Один шаг = один коммит с осмысленным сообщением. Не смешивай шаги.
3. **Каждый шаг заканчивается проверкой** из блока «Критерий готовности». Если проверка требует сервера – пометь, что локально не проверено.

## Git-процесс (как работать с ветками)

**Ствол – `main`:** всегда рабочий, с него деплой на сервер (`git pull`). **Прямо в `main` не коммить.**

**Один шаг = одна ветка = один PR:**
1. `git switch main && git pull`
2. `git switch -c <ветка шага>` (имя – в таблице ниже)
3. реализуй шаг (лучше один осмысленный коммит) → `git push -u origin <ветка>` → открой PR в `main`
   - на PR автоматически запускается **CI** (`.github/workflows/ci.yml`): `ruff check`, `ruff format --check`, импорт-проверка, `pytest`. Прогоняй их локально ДО пуша — красный CI = PR не готов к ревью
   - CI ставит только extra `dev`: симулятор (`sim`) и CUDA-torch (`train`) там не поднимаются, всё симуляционное проверяется на сервере
4. дождись **ревью** (Opus); правки – в ту же ветку
5. после аппрува – merge в `main`, ветку удали
6. следующий шаг ответвляй от **обновлённого** `main` (так подтянется предыдущая работа; заранее все ветки не создаём – шаги зависят друг от друга)

**Карта веток (что где разрабатывать):**

### Шаг 1.2 – Сцена: 2× SO-100 + простой кубик (плумбинг, без артикуляции)
> Цель шага – завести «трубопровод» (две руки + мультиагентные наблюдения/действия + обучаемый сигнал награды) на ПРОСТОМ кубике, до сложной артикуляции.

**Файлы:** `callosum/envs/two_so100_base.py`, `scripts/smoke_env.py`.
**Читать перед этим:** `two_robot_stack_cube.py`, `so_100.py` (на теге `v3.0.1`).

**Проверено в `so_100.py` @ v3.0.1 (можно опираться):** `@register_agent()` → `class SO100(BaseAgent)`, `uid = "so100"`; контроллеры — только `pd_joint_pos`, `pd_joint_delta_pos`, `pd_joint_target_delta_pos` (**`pd_ee_delta_pose` отсутствует** — IK-контроллера у SO-100 нет, поэтому joint-управление безальтернативно); есть `arm_joint_names`, `gripper_joint_names`, свойства `tcp_pos` / `tcp_pose`.
**Что сделать:**
- Класс `TwoSO100Base(BaseEnv)`, `@register_env("TwoSO100-v0", max_episode_steps=100)`.
- `SUPPORTED_ROBOTS = [("so100", "so100")]`; `agent: MultiAgent[Tuple[SO100, SO100]]`.
- `__init__(self, *args, robot_uids=("so100","so100"), robot_init_qpos_noise=0.02, **kwargs)`.
- Контроллер по умолчанию – `pd_joint_delta_pos`.
- `_load_agent(options)` → `super()._load_agent(options, [sapien.Pose(p=[0,-0.3,0]), sapien.Pose(p=[0,0.3,0])])` (позы двух рук по бокам стола; **проверь досягаемость** – SO-100 маленький, кубик клади в рабочую зону).
- Свойства `agent_a`/`agent_b` → `self.agent.agents[0/1]`.
- `_load_scene(options)` → `TableSceneBuilder` + простой кубик через `actors.build_cube(...)` (размер ~ реального кубика Рубика, ~5.7 см).
- `_initialize_episode(env_idx, options)` → руки в keyframe `rest` + шум `robot_init_qpos_noise`; кубик – фиксированно/слегка рандомно в центре.
- `_get_obs_extra(info)` → **на агента**: свои `qpos/qvel`, поза TCP (`agent_x.tcp.pose`), поза кубика; плюс поза TCP партнёра **под флагом** (см. 1.4, пока всегда включить).
- `evaluate()` → пока заглушка `success=False` (нет цели на этом шаге).
- `compute_dense_reward(obs, action, info)` → простая **reach-награда**: минус расстояние от каждого TCP до кубика (чтобы убедиться, что руки учатся тянуться). `compute_normalized_dense_reward` → делить на макс.
- `scripts/smoke_env.py`: создать env с `num_envs=16`, `obs_mode="state"`, `sim_backend="gpu"`; `reset()`; 20 шагов случайных действий; напечатать формы наблюдений/действий/наград (проверить, что они **по-агентные**).
**Критерий готовности (СЕРВЕР):** `uv run python scripts/smoke_env.py` отрабатывает на GPU; действия/наблюдения – словари по агентам; формы разумные; ошибок нет. На маке – только импорт/линт.

**Что проверю я:** правильный uid `so100`, контроллер `pd_joint_delta_pos`, нет остатков `panda`, обе руки досягают кубик, наблюдения реально по-агентные.

### Шаг 1.3 – «Поворотный» кубик (артикуляция) + задача поворота грани
> Самый сложный шаг. Строим кубик как **артикуляцию**: корпус + один **revolute-сустав** (грань). Ролевая задача: рука A держит корпус, рука B поворачивает грань на 90°.

**Файлы:** `callosum/envs/face_turn.py`, `callosum/envs/_turntable_cube.py` (билдер кубика), `scripts/smoke_face_turn.py`.
**Читать перед этим:** `turn_faucet.py` (это ГЛАВНЫЙ референс: захват и вращение revolute-сустава, награда по углу, успех по порогу), + примеры билдеров артикуляций в `mani_skill/utils/building/`.
**Что сделать:**
- `_turntable_cube.py`: функция, строящая артикуляцию «поворотный кубик» – базовое тело (корпус) + одно звено-«грань» на **revolute joint** (ось = вертикаль верхней грани), лимиты сустава `[0, pi/2]`. Если программный билдер артикуляции окажется сложным – как fallback сделать грань отдельным телом на revolute-суставе к корпусу; оставить `# TODO(review)` с описанием выбора.
- `FaceTurn(TwoSO100Base)`, `@register_env("FaceTurn-v0", max_episode_steps=100)` – переопределяет сцену на «поворотный кубик».
- Роли (фиксированы): `agent_a` = **holder**, `agent_b` = **rotator**.
- `evaluate()`: `success` = угол грани в пределах `tol` от `pi/2` **И** корпус не сместился/не повернулся больше допуска. Вернуть также `face_angle`, `is_body_stable` (булевы тензоры на батч).
- `compute_dense_reward`: сумма термов – (a) rotator тянется к точке захвата грани; (b) захват грани; (c) **прогресс угла** грани к 90° (как в turn_faucet); (d) holder держит корпус у цели; (e) **штраф** за смещение/поворот корпуса. Все термы – тензоры на батч; веса – в конфиге.
- `scripts/smoke_face_turn.py`: как 1.2, плюс проверка, что при **скриптовом** доведении грани до 90° `evaluate()['success']` становится True.
**Критерий готовности (СЕРВЕР):** среда строится; случайный роллаут идёт; скриптовый поворот грани до 90° → `success=True`; корпус-штраф срабатывает при смещении.
**Статус: ✅ выполнено 2026-08-30.** `obs_mode="state"` → (16, 53). Скриптовая проверка: `face_angle = 1.5708` при цели 1.5708 → `success=True`, награда 3.097; смещение корпуса на +5 см по x → `is_body_stable=False`, `success=False`, награда 2.859. Обе стороны критерия подтверждены.
**Что проверю я:** корректность артикуляции (ось/лимиты), награды (единицы, формы, батчинг), детекция успеха (порог/допуски), отсутствие «протечки» центральной инфы в наблюдения.

## ФАЗА 2 – Обучение MARL

> Замечание о риске: мостик «ManiSkill(GPU) → BenchMARL» может оказаться нетривиальным (BenchMARL ждёт PettingZoo-обёртку, а ManiSkill GPU-векторизован). Поэтому:
> - **Сначала** заведи надёжный IPPO, расширив GPU-нативный PPO-пример ManiSkill до двух агентов (гарантированно совместимо с GPU-средой).
> - **Потом** подключай BenchMARL для стандартизированных IPPO/MAPPO и сравнений.

### Шаг 2.1 – Надёжный IPPO (из PPO-примера ManiSkill)
> ⚠️ **Критический путь платной сессии на сервере.** Пишется вслепую (локально не запустить), поэтому качество здесь важнее скорости — см. [`server-runbook.md`](server-runbook.md).

**Файлы:** `callosum/training/ippo.py`, конфиг `callosum/configs/ippo.py` (dataclass, как `configs/face_turn.py`).
**Читать перед этим:** `examples/baselines/ppo/ppo.py` на теге `v3.0.1` — **путь от корня репозитория ManiSkill, а НЕ внутри пакета `mani_skill/`**; в pip-пакете примеров нет, читать только с GitHub. Рядом полезны `ppo_fast.py` и README той же папки.
**Что сделать:**
- Взять GPU-нативный PPO ManiSkill (single-file, CleanRL-стиль) и расширить до **двух независимых политик** (IPPO): у каждой руки свой актор/критик и свой срез наблюдений/действий; шаг среды общий.
- ⚠️ **Действия — dict по агентам** (`MultiAgent`, ключи `so100-0`/`so100-1`), а не один вектор; наблюдение при `obs_mode="state"` — **общий плоский тензор** (см. шаг 1.4). Значит вход политики агента надо **собирать явно** — то же требование продолжится в 3.2.
- Запуск как модуль: `python -m callosum.training.ippo --env-id <id>` (так вызывает runbook).
- **Логирование:** в зависимостях сейчас нет ни `tensorboard`, ни `wandb`. Добавь **`tensorboard`** в extra `train` и пиши скаляры (reward, success-rate, лоссы) в `runs/`. Это единственная новая зависимость, которую можно трогать; остальной лок не менять.
- Число параллельных сред по умолчанию взять консервативно (напр. 256) — на сервере подкрутим.
**Критерий готовности (СЕРВЕР):** сначала sanity на **`TwoSO100-v0`** (чистая reach-награда) — кривая награды растёт; затем `FaceTurn-v0` — success-rate логируется и нетривиален.
**Статус: частично ✅ 2026-08-30.** `TwoSO100-v0`, 1 млн шагов (78 обновлений, 3.5 мин на A100): `train/return` −74.9 → −40.5, `explained_variance` −0.18 → 0.99, `value_loss` 0.065 → 0.0003, `entropy` 5.49 → 3.74, `approx_kl` ≤ 0.033 при `target_kl=0.1` (обновления не обрываются). Sanity-часть критерия выполнена.
**`FaceTurn-v0`, 2 млн шагов (156 обновлений): обучение идёт, задача НЕ решается.** `train/return` 1.69 → 12.12 монотонно и без плато, `explained_variance` −10.3 → 0.99, `entropy` 5.51 → 2.67 — тренер исправен. Но `train/success_once` = 0 во всех 78 точках. Награда 0.121 за шаг против 3.097 у скриптового успеха, то есть ~4%. Разложение: при старте `angle_progress` даёт 0.011, значит на дотягивание приходится ~0.006 → `d ≈ 0.6 м`; к концу ~0.11 → `d ≈ 0.36 м`. Схваты встают в 36 см от цели при разносе оснований `y = ±0.3`. **Диагноз (`scripts/probe_reach.py`, 8192 конфигураций):** кубик **достижим** — лучший подход 0.033 м у ротатора и 0.021 м у холдера, так что разнос `y = ±0.3` корректен и соответствующий `TODO(review)` из шага 1.2 закрыт. Настоящая причина в формировании награды: в стартовой позе схваты стоят в 0.370 м, политика закончила на ~0.36 м, то есть **не сдвинулась с покоя**. Штраф за дрейф корпуса был линейным от нуля и на границе допуска успеха (1 см / 0.1 рад) стоил −0.55 за шаг, тогда как подход с 0.37 до 0.20 м даёт всего +0.19. Подходить было невыгодно, стоять — локальный оптимум. **Исправлено:** штраф сделан шарнирным за пределами допуска, то есть плотная награда приведена в согласие с `evaluate()`. **Не помогло:** повторный прогон на 2 млн дал `eval_return` 11.39 при нуле успехов, тогда как полное бездействие в позе покоя стоит 10.8 — превышение всего 5%, руки по-прежнему не идут к кубику. **Следующий подозреваемый — `gamma = 0.8`:** эффективный горизонт 5 шагов, вес награды через 30 шагов равен 0.0012. Захват и поворот грани отстоят на десятки шагов и для агента практически невидимы. Значение унаследовано из эталона ManiSkill, настроенного на короткие задачи с немедленной наградой. Проверяется `--gamma 0.99` (горизонт 100 шагов) и зондом `scripts/probe_policy.py`, который печатает поведение по шагам и разложение награды по слагаемым.

## ФАЗА 3 – Модуль Bi-JEPA (пространство состояний)

> **Хорошая новость:** это чистый PyTorch → **тестируется на маке** (без симуляции).

### Шаг 3.1 – Энкодер + предсказатель партнёра
**Файлы:** `callosum/agents/bijepa.py`, `tests/test_bijepa.py`.
**Читать перед этим:** [03-method-bijepa.md](thesis/03-method-bijepa.md) (формулировка), глоссарий (энкодер, латент, EMA, stop-grad).
**Что сделать:**
- `Encoder` (MLP): наблюдение агента `o_i` → латент `z_i` (размер в конфиге).
- `PartnerPredictor` (MLP): история своих латентов `z_i` → предсказанный латент партнёра `ẑ_j`.
- Цель `z_j` – из наблюдения партнёра через **target-энкодер**: на старте state-space можно общий энкодер + **stop-grad** на цели (EMA-обновление добавить опцией).
- Функция потерь: MSE в латентном пространстве между `ẑ_j` и `stop_grad(z_j)`.
**Критерий готовности (MAC!):** `tests/test_bijepa.py` – на фиктивных тензорах: формы верны; один forward+backward проходит; `z_j` реально под stop-grad (нет градиента в target). `pytest` зелёный, ruff чисто.

### Шаг 3.2 – Встраивание в политику + вспомогательный лосс + ablation
**Файлы:** правки в `callosum/training/*`, конфиг.
**Что сделать:**
- Подать `ẑ_j` на вход политике агента.
- Добавить JEPA-лосс (шаг 3.1) как **вспомогательный** к RL-лоссу (вес в конфиге).
- Реализовать тумблер `partner_input ∈ {oracle, predicted, none}`: `oracle` = истинный латент партнёра `z_j`; `predicted` = `ẑ_j` (Bi-JEPA); `none` = нули/отсутствие.
- ⚠️ **КРИТИЧНО (вскрылось на шаге 1.4): вход политики надо СОБИРАТЬ ПОАГЕНТНО, нарезая общий вектор наблюдения.** ManiSkill при `obs_mode="state"` отдаёт **один плоский общий** вектор обеим рукам, поэтому env-флаг `partner_obs` физически не может скрыть данные партнёра от конкретного агента. Если подать этот вектор обеим политикам как есть, режим `partner_input="none"` окажется **пустышкой** (данные партнёра всё равно внутри), и **вся ablation-тройка станет недействительной** — а это ядро научной части диплома. Значит: явно построить для агента *i* его входной вектор (своя проприоцепция + своё + предсказанное/истинное/отсутствующее по партнёру) и **написать тест**, что при `none` данные партнёра действительно отсутствуют во входе политики.
**Критерий готовности (СЕРВЕР):** обучение идёт во всех трёх режимах; вспомогательный лосс логируется и убывает.
**Что проверю я:** stop-grad и веса лосса; что в `oracle` не течёт инфа в инференс сверх задуманного; что `predicted` использует **только** своё наблюдение на входе политики.

**Статус (локально завершено, ruff + py_compile + 59 pytest зелёные; server-валидация — runbook §3):**
- `callosum/training/_agent_obs.py` — `partner_input ∈ {oracle, predicted, none}` через `build_policy_input(..., base=None)`: «none» гарантированно **исключает** партнёра (свежий тест `test_build_policy_input_none_excludes_partner_info`), но ширина слота = `latent_dim` во всех режимах → `obs_dims` стабильен.
- `callosum/configs/ippo.py` — `partner_input: str = "none"` + вложенный `bijepa: BiJEPAConfig` (не попадает в CLI).
- `callosum/training/_bijepa_policy.py` — `bijepa_step(encoder, predictor, raw_obs, i, uids, partner_input, latent_dim, context=None)` → `(policy_input, z_i, z_j, z_hat_j)`. **Фаза 1: `context=None`** — текущий `z_i` (length-1), **без** rolling-буфера истории → нет креста-эпизодного/cross-iteration состояния для reset (продуманный слепой failure mode). `LatentHistory` осталась как протестированная утилита для фазы 2 (не провязана в тренер).
- `callosum/training/ippo.py` — shared `BiJEPA` + `bijepa_optimizer` (params E+P disjoint с `Agent`). Кодирование `z_i/z_j/z_hat` в rollout — **вне** `no_grad` (чтобы `z_hat` держал graph); семплинг action/value — внутри `no_grad`. `z_j` буферится **detach()-нутым** (target), `z_hat` — как есть в `list`+`torch.stack` (⚠️ назначение в `buf[step] = z_hat` рвёт graph и бы вынудило enc/p предсказателя никогда не учиться — поймано на этапе ревью, исправлено). Policy-input slot **detach()** внутри `bijepa_step` → `ppo_update` backward не трогает E+P; E+P учатся **только** JEPA aux loss через `bijepa_optimizer` (вес `aux_weight=0.1`), один раз в итерацию, после per-agent PPO updates. Все 5 obs-сайта согласованы (eval, rollout, final_observation, next_value, sizing).
- **Отказ:** EMA-таргет/общий `target_encoder` отложен на Фазу 2 (3.1 uses stop-grad, как специфицировано); rolling latent history — на Фазу 2.
