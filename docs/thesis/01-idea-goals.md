# 01 – Идея, цель, задачи

## Исследовательский вопрос

> Могут ли две децентрализованные руки действовать **согласованно**, если каждая **предсказывает, что делает партнёр** (Bi-JEPA – предсказание латентного состояния партнёра), а не наблюдает это, и без обмена сообщениями?

**Допущения.** Моторика **скриптовая**: низкоуровневые движения – готовые примитивы, они не предмет исследования («моторика скриптовая, исследуется координация исполнения»). Алгоритм сборки (последовательность ходов) задан и **известен обоим агентам**; планирование не обучается. Обучается только **согласованное исполнение** – кто что и когда делает. Это решение принято 2026-10 после того, как joint-level RL оказался упёртым в моторику захвата (см. [04](04-experiment-design.md)).

## Идея

Две руки-манипулятора **SO-ARM101** (открытое железо LeRobot / TheRobotStudio, 5 DOF) с **параллельным захватом Robonine** (две призматические губки), каждая – самостоятельный **агент**, совместно собирают кубик Рубика. Координация **децентрализованная**:

- на исполнении агент видит только **своё** наблюдение (проприоцепция + состояние общего объекта; камера – в фазе со зрением);
- **нет центрального контроллера** и **нет явного обмена сообщениями**;
- согласование («кто держит, кто крутит», синхронизация перехватов) возникает за счёт того, что каждый агент **предсказывает латентное состояние партнёра** – механизм **Bi-JEPA**.

### Декомпозиция задачи

Физическая сборка кубика двумя руками – длинногоризонтная контактная задача, плоский RL на весь солв нереален. Иерархия:

1. **Высокий уровень (готовый солвер):** Kociemba / God's algorithm выдаёт последовательность поворотов граней (~20 ходов). Это классический алгоритм, **не** обучается.
2. **Атомарный примитив координации:** «повернуть грань на 90°/180°» – удержание корпуса одной рукой + твист грани другой, при необходимости переориентация кубика и **смена ролей**. Моторные части (подойти, зажать, повернуть, отойти) – **скриптовые примитивы**; политика каждой руки выбирает, какой примитив выполнять сейчас (**skill-level MARL**, обучается RL + Bi-JEPA).
3. **Полная сборка = цепочка примитивов** по списку солвера.

Именно на уровне атомарного бимануального примитива живёт научная часть: децентрализованная координация ролей «холдер ↔ ротатор» без центрального арбитра – естественная площадка для Bi-JEPA.

### Что обучается, а что берётся готовым

| Компонент                                          | Кто решает                  |
| -------------------------------------------------- | --------------------------- |
| Последовательность поворотов (какие грани крутить) | классический солвер         |
| Низкоуровневое управление руками (моторика)        | скриптовые примитивы (допущение; joint-level RL – вторичная линия) |
| Координация рук (выбор примитива, роли, синхронизация) | RL + Bi-JEPA (обучается) |
| Восприятие состояния кубика (зрение)               | обучается (фаза со зрением) |

## Цель

Разработать и экспериментально проверить **JEPA-подход к децентрализованной координации двух манипуляторов** – не-реконструктивное латентное предсказание состояния партнёра – на задаче бимануальной манипуляции (skill-level: согласованное исполнение скриптовых примитивов), измерив, какую долю разрыва между «без информации о партнёре» и «оракулом» он закрывает. Дальше (опционально) – перенос **sim2real** на реальные SO-ARM101 и сравнение с реконструктивными / дистилляционными подходами к моделированию партнёра.

> Формулировка заострена **после** обзора литературы: базовая идея «латентная децентрализованная координация» уже застолблена (2025–26), поэтому вклад смещён в сторону *JEPA-формулировки* + *sim2real на реальном дешёвом железе* + *систематического сравнения*. См. [02](02-related-work.md).

## Задачи

1. Собрать GPU-симуляцию двух SO-ARM101 с параллельным захватом в ManiSkill; смоделировать кубик (turntable-абстракция → гибридная артикуляция для цепочки ходов). *(готово для turntable)*
2. Построить skill-level среду (`FaceTurnSkills-v0`: дискретные скриптовые примитивы, синхронные решения) и децентрализованный MARL-бейзлайн (IPPO) над примитивами. *(основная линия; вторичная – joint-level IPPO + BC, инфраструктура готова)*
3. Спроектировать и реализовать Bi-JEPA: энкодер наблюдений + предсказатель латента партнёра; интегрировать предсказание в политику. *(модуль готов в ветке `step/3.1-bijepa-module`)*
4. Провести ablation *none / oracle / predicted* (≥3 seeds) и измерить долю разрыва `oracle`–`none`, закрытую Bi-JEPA; затем сравнение с teammate-бейзлайнами (реконструктивный à la Dreamer, дистилляционный à la CLS-DP).
5. (Позже, опционально) Ввести зрение (V-JEPA 2) и выполнить перенос sim2real на реальные SO-ARM101.
6. Свести результаты, сформулировать выводы.

## Ключевые проектные решения (сводка)

| Параметр  | Решение                                                               |
| --------- | --------------------------------------------------------------------- |
| Платформа | Sim2Real (учим в симуляции → переносим на железо)                     |
| Парадигма | Децентрализованный Multi-Agent RL + Bi-JEPA поверх                    |
| Основная линия | **Skill-level MARL**: дискретные скриптовые примитивы, решения раз в ~0.5 с, шаг 2.3 плана |
| Моторика | Скриптовая (явное допущение); joint-level IPPO + BC – вторичная линия |
| JEPA      | Адаптация существующих (V-JEPA / world-model JEPA от Meta), не с нуля |
| Железо    | 1× A100 80GB (сервер лаборатории)                                     |
| Робот     | SO-ARM101 + параллельный захват Robonine; сейчас фокус на симуляции, реальное железо скорее всего не используется (решение по sim2real – отдельно) |
| Стратегия | Сначала skill-level бейзлайн (`oracle`/`none`), потом Bi-JEPA; state-space → vision |
| Вычисления | Тяжёлые расчёты (сим, демо, обучение) – только на GPU-сервере |

Детали и обоснования решений – в [03](03-method-bijepa.md), [04](04-experiment-design.md), [05](05-stack-environment.md).
