# Docking-v0: спецификация кандидата на hidden-partner эксперимент

Статус: **proposal** (2026-11-21). Реализовывать после OccludedToss-v0, если гипотеза
«Bi-JEPA помогает при скрытом партнёре» подтвердится на существующей задаче.

## Зачем

Простые coop-задачи (cart-pole, pendulum, toss) оказались реактивно достаточными: партнёр виден
через общий объект, `predicted` не даёт выигрыша. Docking — задача, где партнёрский **замысел**
(target's intent) принципиально скрыт: второй корабль (target) имеет приватную цель/манёвр, а
chaser видит только собственное состояние и зашумлённую/задержанную относительную позицию.
Именно здесь латентное предсказание партнёра (Bi-JEPA) должно давать преимущество над `none`.

## Физика (2D, аналитическая, GPU-only)

- Два тела: `chaser` и `target`, каждое — точка с массой и ориентацией (или 2D rigid body с θ).
- Состояние: позиция `(x, y)`, скорость `(vx, vy)`, ориентация `θ`, угловая скорость `ω`.
- Управление: непрерывные thrusters — 2D сила `(Fx, Fy)` + момент `τ` (нормированные; лимиты
  per-agent, gain/latency — приватные, как в suite).
- Динамика: ньютоновская, `dt=0.02`, `control_every=4` (0.08 c на control step), трение/демпфирование.
- Домен: относительное расстояние ≤ ~10 м, скорости ≤ ~1 м/с; стыковка = совпадение позиции,
  скорости и ориентации в допусках одновременно.

## Скрытый партнёр (суть эксперимента)

- **Target** имеет приватную цель: желаемую точку стыковки `p*` (случайная в пределах дока) и/или
  скрытый боковой импульс/манёвр (`impulse`, время срабатывания), которые chaser не наблюдает.
- **Chaser** видит: своё состояние, зашумлённую и/или задержанную относительную позицию/скорость
  (`measurement_noise`, `measurement_delay` 0.1–0.4 c), цель стыковки (общую), время.
- **Target** видит свою цель и относительное состояние (полное или частичное); его политика —
  часть кооперативной пары (общая team-reward на успех стыковки).
- `oracle`: chaser получает полное состояние партнёра + его приватную цель (верхняя граница).
- `predicted` (Bi-JEPA): латент партнёра (`ẑ_target`) предсказывается из истории собственных
  наблюдений/действий chaser'а; вход политики = own obs + `ẑ_target`. В отличие от toss, здесь
  скрыта именно **цель/намерение**, а не поза, поэтому предсказание должно нести полезную информацию.

## Награда / успех

- `success_bonus = +2`, `step_penalty = −0.001`, `failure_penalty = −2`;
  failure — выход за границы домена / относительная скорость > лимита при контакте / таймаут
  (таймаут штрафуется как failure, не как «дешёвый» конец).
- Potential shaping: `−‖p_rel‖/scale − ‖v_rel‖/scale` (telescoping), success — конъюнкция допусков
  (позиция, скорость, ориентация), как в cube/wrench.
- Инвариант неаддитивности: `only-chaser` (target пассивен) не должен достигать успеха ≥ 1.5×
  допуска; `only-target` аналогично.

## Реализация (GPU-first)

- Новый пакет `callosum/experiments/docking/`:
  - `logic.py` — чистые правила (obs layout, success/failure, reward, randomisation) без torch/mujoco;
  - `env_torch.py` — **векторизованный torch env** (батч миров на GPU, без MuJoCo): динамика,
    latency-очереди, приватные параметры, auto-reset; интерфейс как у `CoopBatchGPU`
    (`torch_io=True`, `reset/step`, `finished_*`);
  - `config.py` — конфиг/CLI (`--task docking`, `--mode none|oracle|predicted`);
  - `oracle.py` — централизованный scripted контроллер (может читать полное состояние);
  - `train.py`/`eval.py` — через общий IPPO (`common/ppo_core.py`), GPU-only;
  - `render.py` — 2D/3D схематичный рендер (matplotlib/PIL или MuJoCo визуал без физики), демо.
- Тренер: `python -m callosum.experiments.docking.train --backend torch --num-envs 1024 ...`
  (или расширение `cube_wrench/train.py` веткой `--task docking`; решение при реализации).
- Метрики: success @ 128 эпизодов × 3 held-out сида, `oracle−none`, `predicted−none`,
  время до успеха, доля «мягких» успехов (на границе допусков).

## Протокол

1. Сначала реализовать и провалидировать среду: oracle ≥ 0.95, only-chaser/only-target ≈ 0;
   детерминизм seed, GPU-батч throughput ≥ 50k env-steps/s.
2. Абляция: `none` / `oracle` / `predicted`, 3 сида, 500–1000 апдейтов (до сходимости).
3. Гейт: `predicted` должен обгонять `none` на раннем фиксированном бюджете и/или на асимптотике
   при скрытой цели; иначе — честный отрицательный результат (метод не подтверждён).
4. Демо: успешная стыковка (policy vs oracle), провал/таймаут, попытки с разными seed'ами.

## Риски

- Если target-политика тоже учится, скрытая цель может «протекать» через его действия; для чистоты
  можно фиксировать target scripted (oracle-like) на первом этапе, а затем учить обе стороны.
- Задержка измерения может сделать задачу неразрешимой для `none`; это ок для upper-bound, но
  нужно следить, чтобы `oracle`/`predicted` оставались обучаемыми.
- Новый torch-env дублирует часть harness; переиспользовать `common` и контракт `CoopBatchGPU`,
  не тащить MuJoCo.
