# Runbook: сервер лаборатории через JupyterHub (без SSH)

Вариант доступа, где к машине нельзя подключиться по SSH, а файлы ходят только
через веб-интерфейс JupyterHub. Отличается от [server-runbook.md](server-runbook.md)
(там RunPod + SSH) тремя вещами, каждая из которых требует обхода:

1. **Ядро ноутбука умирает при закрытии вкладки.** Обучение идёт часами, поэтому
   его нельзя запускать прямо в ячейке — нужен отсоединённый процесс.
2. **Файлы ходят только через браузер.** Значит либо репозиторий клонируется на
   сервере из GitHub, либо привозится архивом.
3. **Прав администратора нет.** Всё ставится в домашнюю директорию.

---

## Шаг 0. Зонд — делать первым, до всего остального

Загрузи в JupyterHub **один файл**:

```
notebooks/00_probe_environment.ipynb
```

Открой, выполни `Kernel → Restart & Run All`, пришли вывод целиком.

Он ничего не устанавливает и не меняет — только читает, использует лишь
стандартную библиотеку Python и работает на любом ядре. Отвечает на четыре
вопроса, от которых зависит весь дальнейший план:

| Вопрос                                       | Почему решает всё                                                             |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| Какая карта, сколько памяти, версия драйвера | Определяет, какую сборку CUDA ставить. Blackwell (sm_120) требует CUDA ≥ 12.8 |
| Есть ли исходящий интернет                   | Без него зависимости придётся привозить архивом, а это несколько гигабайт     |
| Сколько свободного места                     | Нужно 100–200 ГБ. В домашних директориях лабораторий часто квота 20–50 ГБ     |
| Переживает ли процесс отключение             | Определяет, как запускать многочасовое обучение                               |

**Не разворачивай окружение, пока не разобран вывод зонда.** Порядок именно
такой, потому что при отсутствии интернета или при жёсткой квоте план меняется
целиком, и время, потраченное на установку, окажется выброшенным.

## Шаг 1. Доставка кода — только архивом

`github.com` недоступен, поэтому клонировать нельзя. Единственный путь — архив,
собранный локально:

```bash
make bundle              # только исходники, ~200 КБ — обычный случай
make bundle VENDOR=1     # + vendor/ с библиотекой PhysX, ~80 МБ
make bundle REF=main     # любой ref
```

По умолчанию в архив идут только исходники. PhysX не меняется и после первой
установки лежит на scratch, поэтому возить его при каждой правке кода незачем.

`VENDOR=1` нужен в одном случае: **scratch очистили** (обычно при перезапуске
пода), и библиотеку надо ставить заново. Признак — `setup_jupyterhub.sh` снова
говорит, что PhysX не найден.

Заливается кнопкой Upload. Распаковать в терминале JupyterHub:

```bash
cd ~ && rm -rf callosum && tar xzf callosum.tar.gz && cd callosum
```

Под капотом `git archive`, поэтому на сервере не окажется ни истории, ни
архивных веток со старыми адресами — только рабочее дерево ветки и `vendor/`.

**Обновления кода** — только новой перезаливкой архива, то есть
`rm -rf callosum && tar xzf callosum.tar.gz`. Это стирает всё внутри
репозитория, поэтому `scripts/setup_jupyterhub.sh` выносит `runs/` в
`~/callosum-runs` и подставляет туда символическую ссылку. Директория в `$HOME`
переживает и перезаливку, и перезапуск пода — в отличие от scratch.

**Не перезаливай архив, пока идёт обучение.** Процесс продолжит писать в
удалённый файл, а результаты пропадут.

## Шаг 2. Развёртывание

Одной командой в **терминале** (`File → New → Terminal`), не в ячейке:

```bash
cd ~/callosum
bash scripts/setup_jupyterhub.sh
```

Скрипт идемпотентный, можно перезапускать. Он делает три вещи, которых нет в
обычном `setup_server.sh`, и каждая обходит конкретное ограничение этой машины:

**Уводит всё тяжёлое на `/tmp`.** В домашней директории 1.1 ГБ свободно, а одно
только окружение с torch и библиотеками CUDA занимает порядка 8 ГБ. Скрипт сам
находит раздел с местом и выставляет `UV_PROJECT_ENVIRONMENT`, `UV_CACHE_DIR`,
`HF_HOME`, а `~/.maniskill` подменяет символической ссылкой — ассеты симулятора
тоже пойдут на `/tmp`. Переменные дописываются в `~/.bashrc`, чтобы работали в
новых терминалах.

**Ставит `uv` из PyPI, а не с `astral.sh`.** Официальный установщик тянет
двоичный файл из релизов GitHub, поэтому здесь он не работает — отсюда и
«curl не работает». `pip install --user uv` проходит, потому что PyPI доступен.

**Проверяет работоспособность, а не импорты.** Реальное матричное умножение на
GPU (`torch.cuda.is_available()` бывает `True` на сборке, которая не запустится
на этой карте), сверка `sm_80` со списком архитектур в сборке torch, импорт
SAPIEN и регистрация обеих сред.

Зависимости ставятся из `uv.lock` командой `uv sync --frozen` — ровно те версии,
что проверены локально, без пересчёта на сервере. В локе нет ни одного пакета с
GitHub, всё с PyPI и `download.pytorch.org`, поэтому блокировка GitHub установке
не мешает.

Первый запуск качает несколько гигабайт и идёт минуты.

**Важно про `/tmp`:** он обычно очищается при перезапуске пода. Исходники в
`$HOME` переживут, окружение — нет. Лечится повторным запуском того же скрипта.

### Почему torch ставится с PyPI, а не с индекса cu128

Первая попытка развёртывания упала здесь, и причина неочевидная:
`download.pytorch.org` на подключение отвечает, но саму загрузку колеса
перенаправляет на `download-r2.pytorch.org` — хранилище Cloudflare R2, которое
фильтр лаборатории блокирует. Проверка доступности фронт-хоста этого не ловит.

Индекс cu128 был прописан ради RTX 5090: Blackwell (sm_120) требует CUDA ≥ 12.8,
чего в колесе с PyPI на тот момент не было. Здесь стоит A100 (sm_80, Ampere),
которую поддерживает любая современная сборка CUDA, так что причина исчезла
вместе со сменой железа. Пин снят, torch резолвится с PyPI (версия 2.13.0),
среда выполнения CUDA приезжает его зависимостями `nvidia-*` — тоже с PyPI.

Как вернуть пин для машины с Blackwell на неограниченной сети — написано
комментарием в `pyproject.toml`.

### Библиотека PhysX — единственное, что приходится привозить руками

При первом импорте SAPIEN скачивает `libPhysXGpu_64.so` из релиза на GitHub, а
GitHub здесь закрыт. Файл привозится вручную.

На машине с доступом к GitHub — качать в `vendor/` внутри репозитория
(директория в `.gitignore`, скрипт развёртывания смотрит туда первым делом):

```bash
mkdir -p vendor && curl -L -o vendor/physx-linux-so.zip \
  https://github.com/sapien-sim/physx-precompiled/releases/download/105.1-physx-5.3.1.patch0/linux-so.zip
```

После этого `make bundle` кладёт архив прямо в `callosum.tar.gz`, и на сервере
`scripts/setup_jupyterhub.sh` находит его в `vendor/` и распаковывает в
`~/.sapien/physx/105.1-physx-5.3.1.patch0/` сам. Отдельная заливка не нужна.

Если архив всё же везётся отдельно, скрипт ищет его ещё и в
`~/physx-linux-so.zip`. Распакованный файл весит 237 МБ, но `~/.sapien` уведена
символической ссылкой на scratch, так что в домашнюю он не ляжет.

Если SAPIEN когда-нибудь запросит другую версию, он назовёт её в тексте ошибки —
тогда поменять `PHYSX_VER` в скрипте и привезти соответствующий архив.

### Ссылка `libcuda.so` — второе, что приходится чинить руками

Симптом:

```
File "sapien/physx/__init__.py", line 64, in enable_gpu
    ctypes.CDLL("libcuda.so", ctypes.RTLD_GLOBAL)
OSError: libcuda.so: cannot open shared object file
```

`libcuda.so` — библиотека **драйвера**, а не набора инструментов CUDA. В
контейнеры среда исполнения NVIDIA пробрасывает с хоста только версионированный
`libcuda.so.1`; символическая ссылка без суффикса обычно приходит с пакетом
разработчика драйвера, которого здесь нет. PyTorch это не задевает, потому что
он линкуется с `libcuda.so.1` напрямую — отсюда и странная картина, где torch
видит GPU, а PhysX нет.

`scripts/setup_jupyterhub.sh` находит `libcuda.so.1` через `ldconfig -p` (с
запасным перебором обычных путей), кладёт ссылку в `$WORK/lib/libcuda.so` и
добавляет эту директорию в `LD_LIBRARY_PATH`, дописывая её в `~/.bashrc`.

**Важное следствие.** Загрузчик читает `LD_LIBRARY_PATH` при старте процесса.
Значит запускать обучение надо **из терминала**, который читает `~/.bashrc`.
Ядро ноутбука, стартовавшее раньше, переменную не увидит, а установка
`os.environ["LD_LIBRARY_PATH"]` внутри ядра уже ничего не изменит — она приходит
слишком поздно. Если работать всё же нужно из ноутбука, ядро придётся
перезапустить после развёртывания.

### Остальные ассеты качать не нужно

Проверено по содержимому колеса `mani_skill` 3.0.1: и модель стола
(`utils/scene_builder/table/assets/table.glb`), и URDF с мешами SO-100
(`assets/robots/so100/`) лежат внутри пакета и загружаются из директории
установки. Наши среды строят кубик процедурно и внешних файлов не требуют,
поэтому блокировка GitHub на них больше никак не скажется.

### Vulkan: нужен даже без отрисовки; чинится подменой загрузчика

Самая длинная история этого окружения, поэтому итог сразу: **системный загрузчик
Vulkan слишком стар для драйвера**. Ставится свежий из conda, подменяется через
`LD_LIBRARY_PATH`, и A100 работает как аппаратное устройство отрисовки.

**Почему устройство вообще нужно.** Загрузчик URDF в SAPIEN создаёт
`RenderMaterial()` для визуальных элементов безусловно — флага, отключающего
разбор визуальной части, у него нет (проверено по исходнику `sapien` 3.0.3,
`wrapper/urdf_loader.py`, `_build_link`). Поэтому ManiSkill не соберёт никакую
среду без Vulkan, при любом режиме наблюдений. Параметр `render_backend="none"`
убирает систему отрисовки из сцены, но не глобальное устройство.

**Симптом.**

```
ERROR: loader_scanned_icd_add: Could not get 'vkCreateInstance' via
       'vk_icdGetInstanceProcAddr' for ICD libGLX_nvidia.so.0
ERROR: vkCreateInstance: Found no drivers!
```

**Причина.** `/usr/lib/x86_64-linux-gnu/libvulkan.so.1` — это `1.3.275` от
апреля 2024. Он слишком стар, чтобы договориться с ICD драйвера 570.x: интерфейс
согласуется, но `vkCreateInstance` возвращает `NULL`. Драйвер при этом полностью
исправен — `vulkaninfo` со свежим загрузчиком (1.4.357) перечисляет A100 как
`DRIVER_ID_NVIDIA_PROPRIETARY`.

Долго вводило в заблуждение то, что `NVIDIA_DRIVER_CAPABILITIES=compute,utility`
и `NVIDIA_VISIBLE_DEVICES=void` — выглядит как «графика контейнеру не выдана».
Проверки это опровергли: библиотеки на месте, `dlopen` проходит, точки входа
экспортируются, `/proc/driver/nvidia/` смонтирован, узлы устройств есть.

**Решение.** `scripts/setup_jupyterhub.sh` ставит свежий загрузчик через conda и
кладёт **символическую ссылку на него одну** в отдельный каталог `$WORK/vklib`,
который и добавляет в начало `LD_LIBRARY_PATH`. Целиком каталог библиотек conda
подставлять нельзя: он вынес бы вперёд ещё и `libstdc++`/`libgcc`, а это ломает
torch.

Подмена делается именно через `LD_LIBRARY_PATH`. Переменная
`SAPIEN_VULKAN_LIBRARY_PATH` выглядит подходящей, но игнорируется, когда
системный `libvulkan` найден — проверено на этом поде.

**Выбор не угадывается, а проверяется.** Скрипт перебирает пары «манифест ×
каталог загрузчика» и на каждой реально конструирует `RenderMaterial()`.
Порядок предпочтения: драйверный ICD со свежим загрузчиком → он же с системным →
lavapipe. Программный растеризатор остаётся последним рубежом: для текущей фазы
его хватило бы (мы не рисуем ни кадра), но фазу 4 он не переживёт.

### Vulkan отсутствует — отрисовка выключена параметром

В этом образе Vulkan не работает: среда исполнения контейнера не пробросила ни
ICD-файл NVIDIA, ни нужные расширения. Проявляется двумя ступенями:

```
UserWarning: Failed to find Vulkan ICD file
[svulkan2] [error] Your GPU driver does not support Vulkan
RuntimeError: vk::createInstanceUnique: ErrorIncompatibleDriver
```

Предупреждение само по себе безобидно, а падает создание сцены: ManiSkill в
`_setup_scene()` добавляет `sapien.render.RenderSystem`, если
`render_utils.can_render()` вернула истину. А эта функция, по признанию
комментария в её собственном исходнике, «не всегда точна» — она проверяет лишь
то, что устройство отрисовки выбрано, а не то, что Vulkan действительно
работает. На headless-контейнере она говорит «да», и следом падает создание
экземпляра Vulkan.

Документированное лекарство — там же, в докстринге `BaseEnv`: отключить
отрисовку параметром `render_backend="none"`.

Для нас это не обходной манёвр, а правильная настройка по существу. Обучение
идёт по состоянию (`obs_mode="state"` / `"state_dict"`), камер нет, ничего не
рисуется — рендерер был чистыми накладными расходами. Параметр проставлен:

| Где | Значение |
|---|---|
| `scripts/smoke_env.py`, `scripts/smoke_face_turn.py` | `"none"` жёстко |
| `IPPOConfig.render_backend` | `"none"` по умолчанию, флаг `--render-backend` |
| `benchmarl_task._make_gym_env` | параметр, по умолчанию `"none"` |

На фазе 4 (зрение) отрисовку придётся включать обратно — `--render-backend gpu`.
К тому моменту Vulkan в контейнере должен заработать, и это отдельный разговор с
администратором лаборатории про `libvulkan1` и параметры запуска пода.

### Файл окружения — источай его перед любой командой

```bash
cd ~/callosum
source .callosum-env.sh
```

Файл создаётся установочным скриптом и содержит уже разрешённые пути: где
окружение Python, где кэши, где `libcuda.so`, какой манифест Vulkan.

Без него `uv run` **молча создаёт второе окружение** прямо в репозитории, потому
что не видит `UV_PROJECT_ENVIRONMENT`. При двух гигабайтах свободного места в
домашней директории это не просто неверно, а опасно. Скрипт установки такой
случайный `.venv` находит и удаляет.

Дописывания в `~/.bashrc` недостаточно: они действуют только в оболочках,
запущенных **после** установки, и не действуют вовсе для `bash script.sh` и для
ядра ноутбука. Файл окружения решает все три случая одной строкой.

## Шаг 4. Как запускать обучение, чтобы оно пережило закрытие вкладки

Главная ловушка JupyterHub. Ячейка `!python -m callosum.training.ippo ...`
умрёт вместе с ядром, как только браузер отключится, и часы счёта пропадут.

Запускать так:

```bash
cd ~/callosum
mkdir -p runs
nohup uv run python -m callosum.training.ippo \
    --env-id TwoSO100-v0 --total-timesteps 50000 \
    > runs/sanity_twoso100.log 2>&1 &
echo "PID: $!"
```

`nohup` отвязывает процесс от терминала, `&` уводит в фон, перенаправление
сохраняет весь вывод в файл. Процесс переживёт и закрытие вкладки, и разрыв
соединения.

Наблюдать за ходом:

```bash
tail -f runs/sanity_twoso100.log     # в терминале
```

```python
!tail -40 runs/sanity_twoso100.log   # в ячейке, если терминала нет
```

## Измеренная пропускная способность (A100, 2026-08-30)

`num_envs=256`, `num_steps=50` → батч 12 800 шагов на итерацию. Установившаяся
скорость **≈3700 шагов/с** (первые итерации медленнее: 2300 → 3200 → 3700, идёт
прогрев). Отсюда реальная цена прогонов:

| Бюджет | Обновлений политики | Время | Для чего |
|---|---|---|---|
| 50 000 | 3 | 15 с | только проводка: не падает, формы сходятся |
| 500 000 | 39 | 2 мин | первый намёк на динамику |
| 1 000 000 | 78 | 5 мин | **разумная проверка обучаемости** |
| 10 000 000 | 781 | 45 мин | полный прогон для итоговых чисел |

Из этого следует поправка к планированию: тройка ablation по 10 млн шагов на
режим занимает около **2,5 часов**, а не дней. Экономить на длине прогонов здесь
незачем — узкое место не в вычислениях.

И предупреждение: **50 000 шагов — это три обновления политики**. По трём точкам
о наличии обучения судить нельзя. Для вопроса «растёт ли награда» минимум
500 000, лучше миллион.

## Окно оценки должно вмещать эпизод

Обе среды зарегистрированы с `max_episode_steps=100`, а `num_eval_steps` по
умолчанию было 50. Итог: за окно оценки **ни один эпизод не завершался**, каждая
оценка печатала `evaluated 400 steps, 0 episodes`, и весь блок метрик `eval/*`
оставался пустым — так прошли оба прогона 30 августа.

Значение поднято до 100. Если менять `max_episode_steps` в среде, `num_eval_steps`
надо поднимать следом, иначе оценка молча перестанет что-либо показывать.

Отдельно: для `TwoSO100-v0` метрика успеха бессмысленна в любом случае — там
`evaluate()` заглушка, всегда возвращающая неуспех. Ориентироваться надо на
`train/return`.

## Шаг 6. Смотреть метрики

TensorBoard внутри JupyterHub:

```python
%load_ext tensorboard
%tensorboard --logdir runs
```

Если расширение не работает (частое ограничение прокси в JupyterHub), метрики
читаются напрямую из файлов событий:

```python
from tensorboard.backend.event_processing.event_accumulator import EventAccumulator
import glob

for d in sorted(glob.glob("runs/*/")):
    ea = EventAccumulator(d)
    ea.Reload()
    tags = ea.Tags()["scalars"]
    print("\n", d, "\n  теги:", tags[:12])
    for tag in ["losses/jepa_loss", "eval/success_once", "train/return"]:
        if tag in tags:
            vals = [e.value for e in ea.Scalars(tag)]
            print(f"  {tag}: первое={vals[0]:.4f} последнее={vals[-1]:.4f} точек={len(vals)}")
```

Второй способ надёжнее и его вывод можно просто скопировать в чат.

## Чего в этом окружении не будет

- **Отрисовки и видео.** Требуют Vulkan/EGL, которых на headless-машине лаборатории
  обычно нет и поставить без прав администратора нельзя. Для обучения по
  состоянию это не нужно; для фазы зрения понадобится отдельный разговор с
  администратором.
- **Произвольных портов.** JupyterHub проксирует только себя, поэтому wandb и
  прочие внешние дашборды могут не работать. TensorBoard читается из файлов —
  см. шаг 6.
- **Гарантии времени жизни.** На общих машинах лаборатории процессы могут
  убиваться планировщиком. Поэтому чекпоинты сохраняются каждые `eval_freq`
  итераций, а не только в конце.
